# Hermes: shared configuration and core skills

Version: 1.2 | Last reviewed: 2026-10-20 | Status: current | Scope: every consumer that runs the
Hermes agent

Consumers that work through the [Hermes agent](https://hermes-agent.nousresearch.com/docs) share
two things from here: the configuration and plugin practice that proved itself
([configurations.md](configurations.md)), the token-efficiency policy over it
([token-efficiency.md](token-efficiency.md)) and a set of skills anyone can load. Everything else a
consumer's agent knows stays with that consumer.

## 1. The naming rule

- **`core-` skills are shared.** A skill whose name starts with `core-` lives in
  `hermes/skills/core-<name>/` in this repo, holds no business data, and is installed into every
  consumer by the sync below. It is owned here: a consumer never edits its installed copy, it
  changes the skill by pull request to this repo.
- **Every other skill is the consumer's own.** Business procedures, names, systems and people stay
  in the consumer's skills directory and never come here. No consumer skill may use the `core-`
  prefix.
- A shared skill follows the same agnostic rules as any doc: no employer, product, host, tenant,
  person or id (`checks/check-sanitised.py` scans this folder too).

## 2. What ships today

| Skill | Holds | Source |
|---|---|---|
| `core-practices` | Every registered rule, grouped by doc, with the stacks it applies to and how it is checked. Loaded before any build, fix or review so the agent works to the current standards | Generated by `hermes/build_skills.py` from `standards/rules.json` |
| `core-token-economy` | The short form of `configurations.md` section 11: recall dropped shell output, what a filter or terse voice must never touch, how to measure | Hand written in `hermes/skills/core-token-economy/` |
| `core-local-model` | The short form of `configurations.md` section 13: the real per-slot window, concurrency caps for cron, kanban and sessions, and reading a failure on a local model. Only for consumers running a model on their own hardware. | `configurations.md` section 13 |
| `core-consumer-report` | The procedure for this account's upward report: collect machine, design, design diff, functionality, practice and gap data from real state, sanitise it, check it, and update the account's single `consumer-report` issue (CONTRIBUTING.md "Reporting from a consumer"). Run on demand with the one-line command in CONSUMING.md section 7. | Hand written in `hermes/skills/core-consumer-report/` |

Plugins and third-party skills are not copied by the sync. `hermes/tools.json` holds one decision
per tool (adopt, adapt or reject, with the reason and the install command) and
`hermes/nightly.py` installs from it every night (section 5).

`core-practices` is generated. Edit `standards/rules.json` or the docs, then run
`python3 hermes/build_skills.py`. CI runs it with `--check` and fails on a stale copy.

## 3. Consuming

1. Keep a clone of this repo on the release a consumer pins.
2. Run the sync from that clone:

   ```bash
   python3 hermes/sync_skills.py --dest ~/.hermes/skills/core
   ```

   It copies every `core-*` skill into the destination, adds the standards docs at that release as
   the skill's `references/`, removes `core-*` skills that left the core, and records file hashes
   in `.core-skills.json`. A file changed by hand since the last sync is reported and left alone
   (exit 3), so a local edit is never lost silently and never wins silently either.
3. Run it on a schedule so every consumer carries the same practice without anyone repeating
   it. Use `hermes/nightly_sync.sh` [clone-dir] [skills-dest]: it pulls the clone, runs the sync,
   and reports only when something changed or failed, so the schedule entry is silent while
   healthy. Example cron line:

   ```cron
   10 6 * * * $HOME/GitHub/build-standards-core/hermes/nightly_sync.sh
   ```

4. Tell the agent to load `core-practices` before it builds, fixes or reviews anything (one line
   in the consumer's standing instructions).

### Managed hosts (converged from git)

Some consumers are servers whose whole setup is applied from another git repo by a convergence
script, with no person signed in to `gh`. Running `hermes/setup.py` or the nightly job there would
be drift the convergence script does not know about. Such a host consumes the core this way
instead, which is the same deploy-key process CI consumers use (README, "CI that builds the app"):

1. **Pin a release.** The host's own repo records the core tag it consumes in one file (for example
   `CORE_VERSION`). Moving to a new release is a pull request on that file, never a pull on the host.
2. **One read-only deploy key for the host.** Make an ed25519 key pair on the host as the service
   user that runs Hermes, with no passphrase, mode 0600, comment `<host>-<user> read-only`. Back the
   private half up to the secret store straight from the host (never through chat or a terminal
   echo), and ask a core admin to add the public half under Settings > Deploy keys, title
   `<host>-<user>`, with **Allow write access** unchecked.
3. **Verify read, not write.** `git ls-remote --tags` over that key lists the tags; the deploy-key
   list on the core shows it read-only.
4. **Sync from the convergence script.** Check out the pinned tag with
   `GIT_SSH_COMMAND='ssh -i <keyfile> -o IdentitiesOnly=yes'` and run
   `python3 hermes/sync_skills.py --dest <profile home>/skills/core` for every profile, as the
   service user.
5. **Apply only what fits.** Settings from `tools.json` that need a shell (for example `rtk`) do
   nothing for a profile without the terminal toolset. Record that as a reasoned skip, not a gap.
6. **Rotate or revoke** by deleting the deploy key on the core, then repeat step 2. A rebuilt host
   restores the key from the secret store.

## 4. Contributing

Every consumer account belongs to the same owner, who is the final say on the standard. That makes
every consumer account a full contributor: it may open a pull request here, and it may merge its own
pull request once `ci` and `visual` pass. No second reviewer is needed, because the approval would be
the same person. The checks and the rebase rule in [CONTRIBUTING.md](../CONTRIBUTING.md) are what
stand in for review.

- Any shareable improvement found while working in a consumer comes back here in the same piece of
  work: a rule or doc section, a kit change, a check, a configuration entry, a `tools.json`
  decision, or a `core-` skill. Do it from the consumer account you are working in; do not wait for
  another account.
- Only add a tool to `tools.json` when the standard should govern it for every consumer. A plugin
  that one machine happens to run is not a contribution: the nightly job ignores plugins it has no
  decision on.
- A new `core-` skill needs a `SKILL.md` with `name` equal to its folder and a description
  that starts `Use when` (`checks/check-hermes-skills.py`).
- Configuration entries name the setting, the value, why, and the failure it prevents.
- Rebase on the current `origin/main` before pushing and before merging, in your own worktree.
  Never take a whole side of a conflict.

## 5. Keeping a consumer in line

A consumer is set up once with `python3 hermes/setup.py --ui OWNER/REPO` ([CONSUMING.md](../CONSUMING.md)),
which registers the Hermes cron job `core-nightly`. Each night it runs `hermes/nightly.py` from the
core clone:

1. Pull the clone (four tries with backoff). If the job itself changed, the new copy takes over.
2. `sync_skills.py`: install the `core-` skills.
3. `apply_setup.py`: for every required entry in `tools.json` install the binary (brew, then cargo),
   run the plugin's install command and enable it, install skills with `hermes skills install`
   (which runs the Hermes security scan), and apply the listed settings with `hermes config set`.
4. For each UI consumer, compare its `standards.lock` with the newest release and run its
   core-update workflow when it is behind; report a sync pull request still open after a day.

Output lines: `CHANGED`, `RESTART` (restart the desktop app and gateway to load a plugin),
`MISSING` (could not fix, with the manual command), (nothing is reported for plugins the standard has no decision on). A
healthy night prints nothing. Problems exit non-zero, so Hermes sends the failure notice.
`python3 hermes/apply_setup.py --check` shows the Hermes part without changing anything.
Consumers set up before `setup.py` existed call `nightly_sync.sh`, which now hands over to
`nightly.py`, so they gain the new steps without a change on their side.

## 6. The nightly: modes, config version 2, report

`hermes/nightly.py` reads `~/.config/build-standards-core/consumer.json` (version 2).

| `apply` key | Default | Effect |
|---|---|---|
| `hermes`, `binaries`, `ui` | on | Hermes skills and settings, binaries, UI consumers |
| `claude` | off | the Claude Code layer; skipped quietly when the `claude` CLI is absent |
| `safe_restart` | off | the safe restart job (`apply_setup.py --safe-restart`) |
| `report` | on | the upward report (below) |
| `consumption` | on | the consumption feed `consumption.json` (below) |

A version 1 file is migrated in place on the next run (backup `consumer.json.v1.bak`, one line of output).
An explicit choice in a version 1 file is kept; only a missing key takes the new default.

UI consumer modes (`--ui OWNER/REPO=MODE:PATH`):

- `workflow`: approval-gated. Runs the repo's own core-update workflow, which opens the sync pull request
  as a draft for the owner's approval; an open one is reported as awaiting approval, a red one as a problem.
- `ops-center`: for an app only its operator uses. Applies at once, behind a local gate
  (`hermes/ops_center.py`): read the pin from the committed default branch; make an isolated worktree of it
  (uncommitted work is never read or touched); run the gate on the current pin and hold the update if that
  fails (reported as the consumer's failure, once per kind); sync and run the gate again; commit and land
  only when both pass; any failure discards the worktree and the pin stays. The gate is the overlay checks
  plus the consumer's `Gate typecheck`, `Gate build` and `Gate verify` rows in `standards-local/parameters.md`.
  A protected default branch gets a branch, a pull request and an immediate merge. `local` is the old name.
- `vendored`: the repo carries no record of the core. The nightly keeps the release the copy actually
  carries in `~/.config/build-standards-core/vendored/` (override: `CORE_VENDORED_DIR`), found from the
  vendoring tool's pin file (`pin` on the entry) or by matching the recorded source hash against each
  release, never set to the newest release; `python3 scripts/core-status.py --vendored OWNER/REPO`
  prints it and says `behind` (exit 3) when a newer release exists. Approval-gated: a release lands only as
  the vendoring tool's pull request. Registered report only, the record is still written.

Consumption feed (`hermes/consumption.py`): every run writes `~/.config/build-standards-core/consumption.json`
atomically, the one file every ops center's Core consumption panel renders (`standards/local-ops-app.md`
section 19 holds the schema). Read-only on every remote, never posted, never writes to another account's issue.

Upward report (`hermes/report.py`, needs `report_repo`, a PRIVATE intake, in `consumer.json` or
`CORE_REPORT_REPO`; never the core, which is public): each account has one open issue labelled
`consumer-report` in that intake. The text between `<!-- nightly:candidates:start -->` and `...:end -->` lists local parts
that duplicate or extend a kit role, local tokens or classes the UI lint flags, and new local additions.
The issue is edited only when that section changed. The body passes `check-sanitised.py --file` and
`check-consumer-neutral.py --file` first; a hit holds the update and is reported locally. It never opens a
pull request: the owner approves in the issue and the owning account opens the core PR.
